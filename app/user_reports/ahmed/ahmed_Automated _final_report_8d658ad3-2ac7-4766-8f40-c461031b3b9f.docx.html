Chapter 2: System Analysis and Requirements

This chapter details the system analysis, data modeling, and requirements for the automated generation of graduation project reports. It outlines the data structures, user roles, functional requirements, and non-functional characteristics that will guide the system’s design and implementation.

Explanation: The ERD models the core entities in the system: Project, Student, Advisor, and ReportTemplate. A Project is linked to a single Student and Advisor (many-to-one). Project entities can potentially reference templates for pre-existing report structures if required by the project’s specifics. This allows for the use of templates, enhancing report generation efficiency. Primary and foreign keys are designated (PK and FK) for clarity. The diagram helps to visualize how data will be stored and related within the database.

2.2 System Requirements

2.2.1 Clients, Customers, and Users

  • Students: The primary users, responsible for inputting project details (problem statement, methodology, results, etc.). They need a user-friendly interface to quickly and accurately provide the necessary information. A crucial expectation is an intuitive interface to minimize input errors.
  • Advisors: They will need access to the system to track student projects and review generated reports. They need access to comprehensive report details and the option to edit certain areas if necessary.
  • Faculty: Faculty overseeing the system can also monitor student project progress. They would require comprehensive statistics and an overall report visualization dashboard to monitor project completion for the department.

2.2.2 Functional and Data Requirements

  • Input: The system must accept detailed project information (text, diagrams).
  • Storage: Data needs to be stored securely and persistently in a database to enable repeated access.
  • Manipulation: The system needs to process input, format data according to report specifications, perform text generation through the Gemini API, and process diagram creation using PlantUML.
  • Output: A formatted graduation project report (PDF or similar), incorporating both text output from the Gemini API and generated diagrams.

2.2.3 Non-functional Requirements

  • Look and Feel: The FlutterFlow interface will need a clean, modern design. Color schemes, typography, and button designs should align with the university’s branding for a cohesive user experience. Accessibility is crucial to ensure inclusivity.
  • Usability: The interface must be intuitive, allowing users to navigate and input information efficiently. It should provide clear feedback and prevent common errors.
  • Security: Robust authentication and authorization mechanisms are needed to protect sensitive student and project data. Encryption and access control are essential.
  • Performance: The system must generate reports within an acceptable time frame. A clear response time target is needed to ensure efficient and timely use. Scalability is a requirement for the future addition of more users.
  • Portability: The application will target modern web browsers, ensuring cross-platform compatibility (Windows, macOS, Linux).

2.3 Proposed Solutions

  • Utilizing FlutterFlow for the UI/UX to create a dynamic, engaging, and adaptable user experience. This solution allows for efficient development of the interface.
  • Employing the Gemini API for high-quality natural language processing and text generation. This is an appropriate choice given the need to generate report content.
  • Leveraging PlantUML for diagram creation, which will directly translate data into visual representations in the report.
  • Utilizing a relational database like PostgreSQL for data storage, ensuring efficient and organized data management.

2.4 Alternative Solutions

  • Using other AI text generation models or libraries instead of Gemini.
  • Choosing different visualization libraries instead of PlantUML.
  • Implementing the report generation using a different front-end framework instead of FlutterFlow.

These alternatives were considered, but ultimately dismissed due to factors like Gemini’s strong performance in natural language processing, FlutterFlow’s ease of UI/UX development, PlantUML’s efficiency in diagram generation, and overall cost-effectiveness and feasibility in the given timeframe. The choice of these technologies aligns with the project’s goals and constraints.
