Chapter 2: System Analysis and Requirements

This chapter details the system analysis for the “Automated Generation of Graduation Project Reports” project. It outlines the data model, system requirements, proposed solutions, and considered alternatives.

2.1 Data Modeling Diagrams

@startuml Entity(Project) { - ProjectID : INT - ProjectTitle : STRING - Description : STRING - Supervisor : STRING - Student : STRING - Keywords : STRING }

Entity(ReportSection) { - SectionID : INT - SectionType : STRING (e.g., Introduction, System Analysis) - Content : STRING - ProjectID : INT }

Entity(Diagram) { - DiagramID : INT - DiagramType : STRING (e.g., ERD, UML) - Image : STRING - ProjectID : INT }

Relationship(Project, ReportSection, “contains”) Relationship(Project, Diagram, “contains”) @enduml

Diagram Explanation:

The Entity-Relationship Diagram (ERD) depicts the core data structures. The “Project” entity stores information about a project, including its title, description, and associated student/supervisor. The “ReportSection” entity captures the content of each section of the project report (e.g., Introduction, System Analysis). The “Diagram” entity is crucial for storing diagrams generated by PlantUML, including the type of diagram and the image data. Relationships are defined to link project information with relevant report sections and diagrams.

2.2 System Requirements

2.2.1 Clients, Customers, and Users

The primary user is the student, who will input project details, and potentially a supervisor for review. The system is also designed to be a helpful tool for professors who could use it for reviewing student projects. Their needs include ease of inputting project information, clear instructions for completing the report sections, and a concise and well-formatted output. Potential pain points include complex input forms, unreliable or slow report generation, or poorly designed user interfaces.

2.2.2 Functional and Data Requirements

  • Functional Requirements:
    • Input Project Details (Title, description, etc.)
    • Generate Introduction (Based on project details)
    • Generate System Analysis (Based on analysis in the project document)
    • Generate Design, Implementation, Testing, Conclusion, References sections automatically.
    • Allow user to upload or generate diagrams.
    • Provide an output report in PDF or DOCX format.
  • Data Requirements:
    • Input: Project details, diagram descriptions.
    • Storage: Project details, report sections, diagram information in a database.
    • Manipulation: Using the Gemini API to generate the text for various sections.
    • Output: A complete formatted report file, which can include images or diagrams.

2.2.3 Non-functional Requirements

  • Look and Feel Requirements: The user interface (UI) will be designed using FlutterFlow with a modern, clear, and visually appealing aesthetic. Color schemes will be consistent and easy to read.
  • Usability Requirements: The system will be intuitive and user-friendly, guiding the user through each step with clear instructions. Error prevention mechanisms will minimize user mistakes.
  • Security Requirements: Authentication (using user credentials) and authorization (restricting access to sensitive information) will be implemented. Input data will be securely stored in a database.
  • Performance Requirements: The system will generate reports within a reasonable timeframe. Scalability is important to accommodate future growth and a large number of project reports.
  • Portability Requirements: The system will be designed for cross-platform use, offering compatibility across various operating systems (e.g., Windows, MacOS, Linux).

2.3 Proposed Solutions

The proposed solution utilizes a three-tier architecture: a front-end (FlutterFlow), a back-end using Python for API interaction with Gemini and PlantUML, and a database (e.g., PostgreSQL) for storing project data. This approach allows for a separation of concerns and easier maintenance.

2.4 Alternative Solutions

  • Manually Generating Reports: This is the current, less efficient approach, which was not considered viable due to the significant time investment required.
  • Using an existing report generation tool: Although some tools existed, none fully met all the project’s needs, for example in automating report sections.
  • Implementing a custom NLP model: Developing a custom model from scratch would be highly resource-intensive and may not provide superior results compared to a well-established API like Gemini. This was deemed infeasible for the project timeframe and resource constraints.
